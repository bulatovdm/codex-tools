# codex-tools

Личная обвязка Codex CLI: живая настраиваемая строка состояния, защита браузерной интеграции после обновлений и документация по настройке харнеса.

## Установка

macOS, Python 3.9+, установленный Codex по `~/.local/bin/codex`, tmux.

```sh
./install.sh
source ~/.local/share/codex-browser-guard/shell.zsh
cx
```

`cx` запускает Codex с дополнительной строкой внизу терминала. Пользовательские задачи и режимы передаются Codex без изменения: `cx resume`, `cx -m gpt-6.1-sol`, `cx -C /path/to/project`. В `/hooks` один раз проверить и доверить два глобальных определения `codex-tools` из `~/.codex/hooks.json`. Они записывают только номер сессии и рабочую папку в личный каталог конкретного запуска. При изменении определения Codex снова требует доверия. Если доверия ещё нет, строка показывает «сессия не определена»; слушателя чужой сессии за своего не выдаёт. UserPromptSubmit обновляет номер после доверия и после смены сессии.

Пример дополнительной строки:

```text
empirika · бой · empirika.whyme.agency · слушатель шины жив · empirika · браузер: CLI проверен
```

Стандартная строка Codex с моделью, контекстом и лимитами остаётся штатной. Её поля выбираются в `/statusline`. Дополнительная строка — поверхность tmux; это не патч бинарника Codex. В графическом приложении ChatGPT эта строка не отображается.

## Настройка строки

`~/.config/codex-tools/status.json` читается при каждом обновлении, перезапуск не нужен:

```json
{"fields":["environment","address","listener","scope"],"separator":" | "}
```

Поля: `project`, `environment`, `address`, `listener`, `scope`, `browser`. Их можно переставлять и скрывать. Недоступные поля не показываются. Обычный репозиторий показывает своё имя; Empirika определяется по `devops/project.conf` и `devops/support/listeners.sh`. Значения конфигурации читаются как текст, код из репозитория не запускается. `.env` не читается: среда берётся из `EMPIRIKA_BASE_URL` запуска, как у MCP. Проект и актив берутся из файла живого слушателя собственной сессии. Учётные данные и query-параметры адреса в строку не попадают.

```sh
codex-tools status --session SESSION_ID
codex-tools status --session SESSION_ID --json
codex-tools doctor
codex-tools browser
```

`cx` использует отдельный сервер tmux и локальный сервер Codex (`--no-daemon`), чтобы окружение и номер сессии не смешивались с соседними запусками. Пользовательская конфигурация tmux не меняется. Отсоединение: Ctrl-B, затем D; команда возвращения печатается в терминале. Сам запуск не поднимает слушатель шины: это делает агент по проектному протоколу.

## Пустой cx и Work Worker

Если проект уже подключён через Work Worker connect, а project MCP включён,
новый `cx` без задачи автоматически выполняет один короткий служебный ход и отвечает
`WW_SESSION_READY`. Native hooks получают настоящий ID; вручную писать для регистрации
не нужно. Это один ход модели, не фоновый polling. Доверие hooks остаётся штатным.

Перед запуском вызывается readonly `work-worker startup-context` только для выбранной
папки, с пределом1.5s. Он не подключает проект и не поднимает broker. Отсутствующий
Work Worker, disabled MCP, timeout/error/неверный ответ сохраняют обычный запуск.
Поддержаны известные параметры нового запуска, в том числе `-C/--cd`, `-m/--model`.
Задачи, `resume`/`fork`/picker, profile/config overrides, remote/worktree и неизвестные
options не получают служебный prompt. Существующий exact UUID resume bootstrap Work
Worker сохраняется. Проекты без private connect opt-in не затрагиваются.

`WORK_WORKER_HOME` берётся из терминала и хранится только в private `launch.json`.
Перед native запуском восстанавливается как заданное значение, так и его отсутствие:
вложенный tmux shell не подменяет runtime значением из zshenv. Персональные значения
не записываются в репозиторий. Global hooks, shell settings и native режим не меняются.

## Если запуск заканчивается `[exited]`

При ненулевом коде Codex обвязка показывает конкретную строку ошибки в терминале,
сохраняет каталог запуска и печатает его путь. Для отсутствующей сессии объясняет
проблему с ID; неполный UUID сопровождается длиной и подсказкой скопировать его
целиком. Выбрать разговор вручную можно командой `cx resume`.
В нём остаются `exit-code`, `launch.json` и, если tmux смог снять свою панель,
`terminal-error.log` с последними 200 строками экрана. Это личные данные вне Git;
terminal log создаётся с правами 0600. Успешные завершения очищаются как прежде.
Сам `[exited]` — сообщение tmux о завершении программы; причина ошибки находится
в сохранённом выводе. Ошибка снятия панели не меняет исходный код завершения Codex.

## Хранение истории Codex

Отдельный инструмент (Python 3.11+ в `PATH`):

```sh
codex-tools history                         # проверка без записи
codex-tools history --apply                 # применить
python3 scripts/history.py --apply          # напрямую из репозитория
codex-tools history --config /path/to/config.toml --apply
```

По умолчанию выбирается `$CODEX_HOME/config.toml` или `~/.codex/config.toml`.
Инструмент явно устанавливает `[history] persistence = "save-all"` и удаляет
`history.max_bytes`, если лимит задан. Также обрабатывает history в старых
`[profiles.NAME.history]`. Отдельные файлы профилей `NAME.config.toml` можно
обработать через `--config`. Установка сама эту настройку не применяет.

В [официальном справочнике Codex](https://developers.openai.com/codex/config-reference/)
`history.max_bytes` ограничивает размер `history.jsonl`, удаляя старые записи.
Без этого параметра лимита нет. `history.jsonl` — история ввода CLI; полные
сохранённые разговоры хранятся отдельно. Документированной настройки удаления
локальных сессий по возрасту, аналогичной `cleanupPeriodDays` Claude Code, нет.
Инструмент не меняет файлы сессий, архивы, хуки или обслуживание базы Codex.

Перед изменением создаётся копия `config.toml.history-backup-TIMESTAMP` с правами
0600 рядом с конфигом. Запись атомарная, повторный запуск ничего не переписывает.
Чужие параметры и комментарии сохраняются. Неоднозначная форма history
(например inline table или dotted keys вместо явной таблицы) приводит к отказу
без изменения конфига. Для восстановления скопируйте резервную копию обратно.
Новые настройки будут прочитаны при следующем запуске Codex; существующие
переопределения через `-c` или конфиги проектов могут иметь приоритет.

Проверки инструмента: `python3 -m unittest discover -s tests -p test_history.py -v`
(Python 3.11+; системный Python 3.9 пропускает их).

## Что устанавливается

- `~/.local/share/codex-tools/scripts` — рабочие копии скриптов;
- `~/.local/bin/codex-tools` и `cx` — запуск и диагностика;
- `~/.local/share/codex-browser-guard` — сторож, состояние, журнал и резервные копии;
- `~/Library/LaunchAgents/com.dima.codex-browser-guard.plist` — проверка каждые 30 секунд и при изменениях;
- два глобальных хука в `~/.codex/hooks.json` — привязка строки к своей сессии;
- дополнение `.zprofile` и `.zshrc`, без изменения пути установленного Codex.

Повторная установка сохраняет настройки строки, чужие хуки и строки оболочки. Изменяемые файлы предварительно копируются в `~/.local/share/codex-tools/backups`. Секреты, личный `config.toml`, транскрипты и состояние в git не входят. Исходники меняются здесь, затем устанавливаются `./install.sh`.

## Проверки

```sh
/usr/bin/python3 -m unittest discover -s tests -v
```

Стандартная библиотека Python; сетевых запросов и работы с данными проекта в пробах нет. Проверяются восстановление после обновления, отказ несовместимому CLI, сохранение чужой конфигурации, идемпотентность установки, изоляция сессий, живость процесса, среда и порядок полей.
