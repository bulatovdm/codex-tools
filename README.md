# codex-tools

Личная обвязка Codex CLI: живая настраиваемая строка состояния, защита браузерной интеграции после обновлений и документация по настройке харнеса.

## Установка

macOS, Python 3.9+, установленный Codex по `~/.local/bin/codex`, tmux.

```sh
./install.sh
source ~/.local/share/codex-browser-guard/shell.zsh
cx
```

`cx` запускает Codex с дополнительной строкой внизу терминала. Пользовательские задачи и режимы передаются Codex без изменения: `cx resume`, `cx -m gpt-6.1-sol`, `cx -C /path/to/project`. В `/hooks` проверить и доверить глобальные определения `codex-tools` из `~/.codex/hooks.json`: два обработчика привязки сессии и обработчики уведомлений ниже. Хуки привязки записывают только номер сессии и рабочую папку в личный каталог конкретного запуска. При изменении определения Codex снова требует доверия. Если доверия ещё нет, строка показывает «сессия не определена»; слушателя чужой сессии за своего не выдаёт. UserPromptSubmit обновляет номер после доверия и после смены сессии.

Пример дополнительной строки:

```text
empirika · бой · empirika.whyme.agency · слушатель шины жив · empirika · браузер: CLI проверен
```

Стандартная строка Codex с моделью, контекстом и лимитами остаётся штатной. Её поля выбираются в `/statusline`. Дополнительная строка — поверхность tmux; это не патч бинарника Codex. В графическом приложении ChatGPT эта строка не отображается.

## Настройка строки

`~/.config/codex-tools/status.json` читается при каждом обновлении, перезапуск не нужен:

```json
{"fields":["environment","address","listener","scope"],"separator":" | "}
```

Поля: `project`, `environment`, `address`, `listener`, `scope`, `browser`. Их можно переставлять и скрывать. Недоступные поля не показываются. Обычный репозиторий показывает своё имя; Empirika определяется по `devops/project.conf` и `devops/support/listeners.sh`. Значения конфигурации читаются как текст, код из репозитория не запускается. `.env` не читается: среда берётся из `EMPIRIKA_BASE_URL` запуска, как у MCP. Проект и актив берутся из файла живого слушателя собственной сессии. Учётные данные и query-параметры адреса в строку не попадают.

```sh
codex-tools status --session SESSION_ID
codex-tools status --session SESSION_ID --json
codex-tools doctor
codex-tools browser
```

`cx` использует отдельный сервер tmux и локальный сервер Codex (`--no-daemon`), чтобы окружение и номер сессии не смешивались с соседними запусками. Пользовательская конфигурация tmux не меняется. Отсоединение: Ctrl-B, затем D; команда возвращения печатается в терминале. Сам запуск не поднимает слушатель шины: это делает агент по проектному протоколу.

## Возврат в оставшийся запуск

Закрытие терминала может отсоединить tmux, сохранив Codex и фоновые задачи.
`cx resume` сначала показывает живые запуски текущей папки: выберите номер для
возврата или0/Enter для обычного списка сохранённых разговоров. EOF/Ctrl-C
отменяют выбор. Если живых запусков нет, сразу открывается штатный список.

`cx resume <полный UUID>` возвращает в единственный отсоединённый запуск этого
разговора, в том числе из другой папки. Его прежние окружение и рабочая папка
сохраняются. Если терминал уже подключён или найдено несколько живых запусков,
команда сообщает об этом без перехвата терминала. Завершённые запуски и старые
metadata без живой pane не используются; conversation locks не изменяются.

Возврат применяется только к этим двум простым формам. `cx` создаёт новый запуск;
`fork`, `resume --last`, модель/config/другие overrides передаются обычному Codex.
Выбор занятого разговора через штатный native picker всё ещё может показать
его собственное предупреждение: для возврата используйте предложенный живой запуск.

## Пустой cx и Work Worker

Если проект уже подключён через Work Worker connect, а project MCP включён,
новый `cx` без задачи автоматически выполняет один короткий служебный ход и отвечает
`WW_SESSION_READY`. Native hooks получают настоящий ID; вручную писать для регистрации
не нужно. Это один ход модели, не фоновый polling. Доверие hooks остаётся штатным.

Перед запуском вызывается readonly `work-worker startup-context` только для выбранной
папки, с пределом1.5s. Он не подключает проект и не поднимает broker. Отсутствующий
Work Worker, disabled MCP, timeout/error/неверный ответ сохраняют обычный запуск.
Поддержаны известные параметры нового запуска, в том числе `-C/--cd`, `-m/--model`.
Задачи, `resume`/`fork`/picker, profile/config overrides, remote/worktree и неизвестные
options не получают служебный prompt. Существующий exact UUID resume bootstrap Work
Worker сохраняется. Проекты без private connect opt-in не затрагиваются.

`WORK_WORKER_HOME` берётся из терминала и хранится только в private `launch.json`.
Перед native запуском восстанавливается как заданное значение, так и его отсутствие:
вложенный tmux shell не подменяет runtime значением из zshenv. Персональные значения
не записываются в репозиторий. Global hooks, shell settings и native режим не меняются.

## Если запуск заканчивается `[exited]`

При ненулевом коде Codex обвязка показывает конкретную строку ошибки в терминале,
сохраняет каталог запуска и печатает его путь. Для отсутствующей сессии объясняет
проблему с ID; неполный UUID сопровождается длиной и подсказкой скопировать его
целиком. Выбрать разговор вручную можно командой `cx resume`.
В нём остаются `exit-code`, `launch.json` и, если tmux смог снять свою панель,
`terminal-error.log` с последними 200 строками экрана. Это личные данные вне Git;
terminal log создаётся с правами 0600. Успешные завершения очищаются как прежде.
Сам `[exited]` — сообщение tmux о завершении программы; причина ошибки находится
в сохранённом выводе. Ошибка снятия панели не меняет исходный код завершения Codex.

## Хранение истории Codex

Отдельный инструмент (Python 3.11+ в `PATH`):

```sh
codex-tools history                         # проверка без записи
codex-tools history --apply                 # применить
python3 scripts/history.py --apply          # напрямую из репозитория
codex-tools history --config /path/to/config.toml --apply
```

По умолчанию выбирается `$CODEX_HOME/config.toml` или `~/.codex/config.toml`.
Инструмент явно устанавливает `[history] persistence = "save-all"` и удаляет
`history.max_bytes`, если лимит задан. Также обрабатывает history в старых
`[profiles.NAME.history]`. Отдельные файлы профилей `NAME.config.toml` можно
обработать через `--config`. Установка сама эту настройку не применяет.

В [официальном справочнике Codex](https://developers.openai.com/codex/config-reference/)
`history.max_bytes` ограничивает размер `history.jsonl`, удаляя старые записи.
Без этого параметра лимита нет. `history.jsonl` — история ввода CLI; полные
сохранённые разговоры хранятся отдельно. Документированной настройки удаления
локальных сессий по возрасту, аналогичной `cleanupPeriodDays` Claude Code, нет.
Инструмент не меняет файлы сессий, архивы, хуки или обслуживание базы Codex.

Перед изменением создаётся копия `config.toml.history-backup-TIMESTAMP` с правами
0600 рядом с конфигом. Запись атомарная, повторный запуск ничего не переписывает.
Чужие параметры и комментарии сохраняются. Неоднозначная форма history
(например inline table или dotted keys вместо явной таблицы) приводит к отказу
без изменения конфига. Для восстановления скопируйте резервную копию обратно.
Новые настройки будут прочитаны при следующем запуске Codex; существующие
переопределения через `-c` или конфиги проектов могут иметь приоритет.

Проверки инструмента: `python3 -m unittest discover -s tests -p test_history.py -v`
(Python 3.11+; системный Python 3.9 пропускает их).

## Уведомления на телефон

После установки и доверия в `/hooks` скрипт `scripts/notify-phone.py` работает и в
обычном Codex, и в `cx`. Нужен `curl` в PATH. Уведомления:

- `💬 Waiting for your reply` — через 30 секунд после `Stop`, один раз на реплику человека;
- `🔐 Needs permission` — если запрос разрешения человеку остаётся незавершённым
  30 секунд, один раз на конкретный запрос; автоматическая проверка не уведомляет;
- `❓ Codex asks you a question` — если вопрос `request_user_input` или
  `request_user_input_async` остаётся без ответа 30 секунд, один раз на конкретный вызов;
- `⚠️ Codex stopped unexpectedly` — при внезапном исчезновении наблюдаемого локального
  процесса или ненулевом завершении через `cx`, кроме штатного Ctrl-C.

Пока вопрос не закрыт, последующий `Stop` не создаёт дополнительный пуш «жду ответа».
Ответ через инструмент, новая реплика, ошибка/отмена вызова, Interrupt и SessionEnd
снимают соответствующее ожидание. Для async-вопроса успешная постановка вопроса
считается продолжающимся ожиданием до ответа человека.

`PermissionRequest` вызывается и при автоматической проверке разрешений, когда
человек не нужен. Хук читает последний `turn_context` из транскрипта и не отправляет
пуш при `approvals_reviewer=auto_review` или `approval_policy=never`. Контекст читается
последовательно с сохранением позиции и известных настроек, поэтому большой вывод
инструмента не вытесняет признак автоматической проверки.
Остальные запросы разрешения получают отдельный таймер `INPUT_NOTIFY_SECONDS`
(по умолчанию 30 секунд); выполнение инструмента, Stop, прерывание, закрытие
сессии или новая реплика отменяют его. Повторная доставка одного события не
порождает новые пуши. Запросы различаются по turn/call ID, а при отсутствии
call ID — по хешу имени и аргументов инструмента; сами аргументы не сохраняются.
Без читаемого `turn_context` автоматический режим определить нельзя: остаётся
отложенная отправка с отменой по событиям.

Новая реплика человека, новый `Stop`, вызов инструмента, прерывание и завершение
сессии отменяют старый таймер. Дополнительно проверяются новые записи активности
в транскрипте: продолжение модели другим Stop-хуком не должно давать ложный пуш.
Служебная инициализация и входящая почта Work Worker, известные task/cross-session
сообщения, включая `Work Worker startup signal`, не сбрасывают ограничение «один пуш
на реплику». Повторный UserPromptSubmit с тем же turn ID также не сбрасывает его.
До первой человеческой реплики пуша о завершении ответа нет. Неизвестные форматы синтетических промптов могут
потребовать дополнить фильтр.

`PreToolUse`/`PostToolUse` отслеживают незавершённые shell-вызовы, начатые после
последней реплики. Пока такой вызов не завершён, пуш откладывается максимум на
15 минут от Stop (но не меньше выбранной idle-задержки), затем приходит с пометкой
`a background task is still running`. Команды прошлых реплик не учитываются.
Если exec возвращает `session_id` продолжающего работать процесса, он остаётся
учтённым до завершения, видимого в PostToolUse/опросе `write_stdin`.
Известные слушатели `listen-events`, `work-worker listen`, `http.server` и команды
`npm/pnpm/yarn dev` исключены. Неизвестный слушатель или сервер может задержать пуш
до этого предела. Сетевые запросы и таймеры выполняются в отдельных процессах:
Codex не ждёт доставки, хук не одобряет запросы разрешений и не добавляет контекст.

Выбор конфигурации: `CODEX_NOTIFY_CONFIG` → `$CODEX_HOME/notify.env`
(обычно `~/.codex/notify.env`) → `~/.claude/notify.env`. Используется первый
существующий файл; явно заданный отсутствующий `CODEX_NOTIFY_CONFIG` отключает
уведомления. Конфиги не объединяются. Если есть конфиг Claude, установщик оставляет
его общим: второй ntfy-топик и перенос токенов не нужны. Если нет ни одного,
установщик создаёт `~/.codex/notify.env` с правами 0600 и случайным ntfy-топиком.
Подпишитесь на этот топик в приложении ntfy на телефоне. Без файла скрипт ничего
не отправляет. Удаление обоих конфигов отключает отправку.

```sh
NTFY_TOPIC=your-existing-topic
NTFY_SERVER=https://ntfy.sh
IDLE_NOTIFY_SECONDS=30
INPUT_NOTIFY_SECONDS=30
BACKGROUND_WAIT_LIMIT_SECONDS=900
# Telegram можно использовать отдельно или одновременно с ntfy:
# TELEGRAM_BOT_TOKEN=...
# TELEGRAM_CHAT_ID=...
```

Файл содержит буквальные `KEY=value`, допустимы кавычки, `export` и комментарии.
Подстановки `$HOME`, `$()`, backticks и другой shell-код не исполняются.
Настройки читаются на событии; уже запущенный таймер использует прежние значения.
Каждый канал имеет таймаут 10 секунд; сбой ntfy не мешает Telegram. Неудачная доставка
повторяется через 5, 10, 20, 40 и далее каждые 60 секунд, пока ожидание актуально.
Принятые сервером каналы сохраняются отдельно и больше не отправляются. Новая реплика,
закрытый вопрос или снятый запрос отменяют устаревшие повторы. Удаление выбранного
конфига также останавливает их. Очередь и подтверждения сохраняются в локальном
состоянии, но повторы выполняет процесс отправки: после перезагрузки машины старые
очереди сами не возобновляются. При потере ответа сервера результат неоднозначен:
ntfy получает постоянный `sequence_id` для обновления прежнего уведомления на
поддерживаемых клиентах; Telegram может получить повтор, если первый запрос был
принят, но подтверждение потерялось.

Заголовок: `Codex · <репозиторий> · <название сессии> [<короткий ID>]`. Короткий ID —
последние восемь символов UUID, чтобы различать сессии одного проекта с одинаковыми
названиями. Начальная папка сохраняется
при `SessionStart` либо берётся из метаданных транскрипта; последующие `cd` её
не меняют. Worktree показывается как `<репо> (<worktree>)`, вне Git — имя папки.
Название берётся только из записи этой сессии в `session_index.jsonl`, если она
есть. Тексты ответа, промпта, команд, причины разрешения и полные пути не отправляются.
Имена проектов и название сессии отправляются в выбранный сервис.
Локальное состояние — `~/.local/share/codex-tools/notify`, отдельное для каждой
сессии, с закрытыми правами; тексты промптов и команд в нём не сохраняются.

Для локальной CLI-сессии хук ищет её собственный процесс Codex среди предков и
запускает отдельный наблюдатель: проверка раз в пять секунд, затем подтверждение
исчезновения через две секунды. PID проверяется вместе со временем запуска.
Штатный SessionEnd и коды выхода `0`, `130`/SIGINT снимают аварийное ожидание.
`cx` дополнительно сообщает фактический код выхода, даже если SessionEnd уже пришёл.
Новые версии `launch.py` применяются к новым запускам `cx`; текущие запуски получают
обновлённый хук на следующем событии. Пуш не содержит экран терминала или текст ошибки.

Отличия от Claude Code и границы поддержки:

- По [официальной документации хуков Codex](https://learn.chatgpt.com/docs/hooks)
  отдельного `Notification`/MCP-elicitation события нет. Встроенные MCP-диалоги
  ввода и фоновые сессии не получают специального пуша; поддержаны видимые вызовы
  инструментов вопросов и `PermissionRequest`.
- Нет отдельного события подтверждения плана. План в конце ответа получает
  обычный `Waiting for your reply`; `update_plan` сам по себе пуш не вызывает.
- Claude `/loop` и `ScheduleWakeup` не переносились. Отдельного надёжного признака
  ожидания собственного запланированного пробуждения здесь нет.
- Формат транскрипта и `session_index.jsonl` не является стабильным API.
  Метаданные `source=exec` и subagent отключают уведомления неинтерактивных запусков.
  Если runtime не передаёт читаемый транскрипт, определить `codex exec`, исходную
  папку и продолжение без хука надёжно нельзя; остаются события и первая `cwd`.
- Отслеживаются только shell-вызовы, наблюдаемые доверенными хуками. Процесс,
  запущенный с `&` внутри уже завершённого shell, и задачи MCP не отслеживаются.
  TCP-порты не сканируются; исключение серверов основано на известных командах.
  `PreToolUse` вопроса означает попытку вызова: другой хук может её отклонить.
- Отдельная отмена async-вопроса вне его результата/ответа человека не имеет
  подтверждённого события; такой вопрос остаётся активным до новой реплики или
  Interrupt/SessionEnd. У общего app-server без собственного CLI-предка нельзя
  надёжно привязать смерть процесса к одной сессии: наблюдатель не назначается
  по догадке. Для полного контроля кода выхода используйте `cx`.
- При выключении всей машины локальный наблюдатель также прекращает работу и
  не может отправить аварийный пуш. Нужен внешний монитор, если требуется этот случай.

Проверки: `python3 -m unittest discover -s tests -p test_notify_phone.py -v`.
Используется подставной `curl`: настоящие пуши, топики и секреты не нужны.
Контракт доставки: [ntfy JSON publish](https://docs.ntfy.sh/publish/#publish-as-json),
[Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).

## Что устанавливается

- `~/.local/share/codex-tools/scripts` — рабочие копии скриптов;
- `~/.local/bin/codex-tools` и `cx` — запуск и диагностика;
- `~/.local/share/codex-browser-guard` — сторож, состояние, журнал и резервные копии;
- `~/Library/LaunchAgents/com.dima.codex-browser-guard.plist` — проверка каждые 30 секунд и при изменениях;
- глобальные хуки в `~/.codex/hooks.json` — привязка строки к своей сессии и уведомления;
- `~/.codex/notify.env` — только если нет собственного или общего конфига Claude;
- дополнение `.zprofile` и `.zshrc`, без изменения пути установленного Codex.

Повторная установка сохраняет настройки строки, чужие хуки и строки оболочки. Изменяемые файлы предварительно копируются в `~/.local/share/codex-tools/backups`. Секреты, личный `config.toml`, транскрипты и состояние в git не входят. Исходники меняются здесь, затем устанавливаются `./install.sh`.

```sh
/usr/bin/python3 -m unittest discover -s tests -v
```

Стандартная библиотека Python; сетевых запросов и работы с данными проекта в пробах нет. Проверяются восстановление после обновления, отказ несовместимому CLI, сохранение чужой конфигурации, идемпотентность установки, изоляция сессий, живость процесса, среда и порядок полей.
